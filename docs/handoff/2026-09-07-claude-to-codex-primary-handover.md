## 3. 最優先の実装依頼

### 3.1 Threads投稿の無限リトライ（Issue #252）🔴

`social_post_queue` の `watch-stop-chasing-sales`（THREADS・caption 454字）が
`THREADS_CREATE_500 Param text must be at most 500 characters long.` で失敗し続けているが、
**FAILED にならず5分ごとに再スケジュールされている。** 実行と外部APIコールを浪費中。

依頼:

1. 投稿前に `caption + link` の合計文字数で判定し、上限超過なら送信前に弾く/切り詰める
2. 4xx系（リトライしても直らないエラー）は即 `FAILED` に落とす。同一エラー N 回で打ち切り
3. `social_post_queue` への INSERT 時点でも上限チェック

詳細と再現SQLは Issue #252。

### 3.2 希望価格ウォッチに `target_product_key` を持たせる 🔴

`public/app.js` のウォッチ保存ペイロードに、モールの商品ID（`record_key` / `asin`）を載せる。

現状、希望価格を設定した3件すべてで
`condition_snapshot.price_condition.target_product_key` が**空**。
商品名だけで毎回モールを探し直しているため、判定を厳しくすれば取りこぼし、
緩くすれば別商品で誤通知、というトレードオフから抜けられない。

## 4. いま壊れている／未確認のもの

### 4.1 希望価格ウォッチ：修正済み・本番未確認 🟡

`src/target-price-watch.mjs` は3時間ごとに動いている。9/7 に実データで2つの不具合を発見し修正。

**不具合1: 別商品で誤通知しうる状態だった**
旧実装は「商品名の先頭12語のうち2語一致で同一商品」。実データの商品名は先頭がキャンペーン文
（`【8/16 23:59まで まとめ買いクーポン3点以上で 10%OFF 】 java ジャバ バッグ … jv1159001`）で
埋まっており、型番 `jv1159001` が判定に入っていなかった。結果、
「全く別のブランド レディース トートバッグ 大容量 軽量」が
「バッグ・レディース・トートバッグ」の3語一致で同一商品と判定されていた。

修正: キャンペーン文を捨て、型番（位置を問わず拾う）とブランド語を必ず見る。
型番一致だけで確定。型番があるのに候補名に無いときは一致率7割。迷ったら通知しない。

**不具合2: 巡回結果が残っていなかった**
「調べた」印だけで価格を残していなかったため、「見つけたがまだ高い」と
「そもそも見つけられなかった」の区別がつかなかった。
`target_price_observations`（migration **0076**、本番適用済み）に結果だけを残す。
会員ID・検索文は入れない。90日保持。

**未確認**: 次の巡回（15:00 JST頃）まで観測0件。切り分けは以下。

```sql
SELECT reason, matched, COUNT(*) n, MIN(price_jpy), MAX(price_jpy), MAX(observed_at)
FROM target_price_observations GROUP BY reason, matched;
```

- `NO_MATCH` ばかり → 判定が厳しすぎ。`IDENTITY_MIN_RATIO`(0.5) / `IDENTITY_STRICT_RATIO`(0.7) を下げる
- `ABOVE_TARGET` → 正常（価格が届いていないだけ）
- `NO_CANDIDATES` → モールAPI側
- 0件のまま → 巡回が回っていない
