## C-1（P2・最優先）楽天 × Yahoo! の同じ商品を 1 つにまとめる
- **原因（Cowork の所見。再現して確定させること）：**
  - `knowledge-search.mjs` の `rankMerchantCandidates`、`index.mjs` の `mergeObservedRankingCandidates`、`product-index-v2.mjs` の候補まとめは、鍵が `asin`／`record_key` だけです。
  - 楽天の API は JAN を返さないので、鍵は常に `RAKUTEN:店:品番` になります（D1 で 11/7 以降 4,155 商品中 JAN 付き 0）。Yahoo! は JAN があると `JAN:…` です。
  - そのため、同じ商品でも別の候補になり、比較欄には片方のモールしか出ません。
- **方針（AI の推測では確定しない。書いてあるものを読むだけ）：**
  1. JAN を持つ候補（Yahoo! など）について、楽天の商品検索 API を `keyword=<JAN>` で引く。返ってきた商品のうち `itemCaption`／`itemName` に**その JAN の 13 桁がそのまま書いてある**ものだけを同じ商品として足す。
     - 呼び出し回数・タイムアウトは既存の予算の中に収めること。応答時間は計測する。
  2. まとめるのは既存の `product-identity-matching.mjs`（＋C-2 の照合）で「同一」とされたものだけ。矛盾があれば別商品。不明なら「同一性未確認」として比較に入れない。
  3. 二重実装しない。`hoshilu-product-normalizer.mjs` の `groupOffersIntoCanonicalProducts` を検索の流れで使えるか先に調べる。
- **必須テスト：** 同じ商品の楽天・Yahoo! の候補があり、条件を満たす実オファーなら、比較欄に両方が出る（固定データで）。
- **完了条件：** 本番で化粧品の評価セット（Cowork が作成中）の商品を QA 検索し、2 店以上で比べられた割合を「前／後」で報告する。誤った同一視は 0。

## C-4（P4）実際に支払う金額
- 楽天 `postageFlag=0`、Yahoo! `shipping.code=2` は「送料込み」と読んでいます。地域ごとの例外（沖縄・離島）や、必須の手数料を API で取れるか調べてください。
- 取れない場合は「送料込み（地域の例外は購入先で確認）」のように、条件として画面に出す案を出すこと。
- ポイント・条件付きクーポンは支払額から引かず、別の表示にする。

## C-5（P5）最安店へ進む表示

## C-7. 計測（KPI）
