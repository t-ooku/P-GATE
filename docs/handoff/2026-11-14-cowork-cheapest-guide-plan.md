# 最安値案内の実現 — Cowork 統括台帳

目指す姿：「買いたい商品があるとき、まずホシルに聞く。どこで買うのが一番安いか分かり、そのまま購入先へ進める」。
まず化粧品で成立させ、日用品・アパレルへ広げる。曖昧検索・写真検索・通知など既存機能は残す。大規模リニューアルはしない。

この台帳が、優先順位・仕様・担当・依頼と受領の正本です。**未着手を着手済みと書かない。** 状態は各担当が自分の受信箱ファイルに書き戻し、Cowork がここへ転記する。

### 分かったこと（根拠つき）

1. **楽天と Yahoo! の同じ商品が 1 つにまとまらない（指示書 §2 の再現原因）。** 候補をまとめる鍵が `asin`／`record_key` だけ。Yahoo! は JAN があると `JAN:…`、楽天は JAN を返さないので常に `RAKUTEN:店:品番`。D1 `price_observations`（11/7〜）で楽天 4,155 商品中 JAN 付き 0、Yahoo! は 1,127 中 522。
   → 楽天と Yahoo! は**同じ商品でも別の候補**になり、比較欄にはそれぞれ片方のモールしか出ない。楽天の中でも、店が違えば同じ #04 が別の候補になる。
2. **ロムアンド「グラスティングカラーグロス」（11/1〜の記録）は、楽天だけで 32 商品ページ。** #04 単品（900〜1,841 円）、S04（別商品）、ミニトリオ、「選べる」ページ（色で値段が変わる）、並行輸入品（商品状態が違う）、01・04・05 のまとめ売りが混ざる。名前だけで同一とすると誤って同一視する。
3. **送料。** 楽天・Yahoo! の API 取り込みと `sanitizePublicOffer` は、送料が確かめられない時の支払総額を 0 にしている（不明を 0 円にはしていない）。ただし比較 API の `realPriceRows` は `total_cost>0` しか見ておらず、送料確認・在庫・確認時刻を見ていなかった。
4. **AI 推定。**
   - 比較 API は、楽天・Yahoo! 以外の 7 モールで AI に価格帯を推定させ、「AI 推定では○○が安い可能性」と名前を出していた。指示書 §4・§6 に反する。
   - `buildAiCheapestRanking` は、送料未確認の商品価格や AI 推定でも「最安」順に並べている（未修正。下の C-3）。
5. **購入先。** カードの購入リンクは `/go?token=` で商品ページへ（署名つき）。比較欄の「価格の安い順で見る」はモールの検索ページ（商品ページではない）。

## 8. 追記（2026-11-14 大隆さん）無効・共通 JAN の対策

指示書への追記（原文）：
> 過去の Issue #706 は SEO からの除外対応であり、価格比較まで修正済みとは限らない。既存対応を確認したうえで、取込から商品キー、同一商品判定、比較、価格履歴、購入先までの経路を点検すること。無効・共通の JAN や店舗内コードだけを根拠に、別店舗の商品を同一商品として統合しない。有効な JAN でも色・容量などが矛盾する場合は要確認とし、最安判定から除外する。無効 JAN が同じ別商品、正しい JAN の同一商品、属性が矛盾する商品を回帰テストに追加。既存の価格履歴の書き換え・削除は別途承認を確認すること。

### Cowork の確認（11/14、読み取りのみ）
- #706 が直したのは `product-detail.mjs` の SEO 判定（`isSeoIndexableKey`）だけ。次の 3 か所は無効 JAN をそのまま使っていた：
  - 取込：`yahoo-shopping-api.mjs` `validJan`（桁数だけ）→ 商品キー `JAN:0000000000000`
  - 同一商品判定：`product-identity-matching.mjs` の JAN／GTIN 一致
  - 検索結果の重複まとめ：`unified-results.mjs` `dedupeKeys`
- D1 `price_observations`（11/7〜11/14）：`JAN:0000000000000` は**今週も記録されている**（10 店・6 商品名・1,180〜4,425 円、最新 11/14）。JAN 付き 522 キーのうち、店内コード・ダミーの形は 5 キー。
- 正しい JAN でも商品名が 2〜4 通りあるキーが 25 以上ある（例 `JAN:4580215052415` は 1,200 円と 2,400 円＝入り数違いの疑い）。「有効な JAN でも属性が矛盾」の実例候補。未精査。
- 本番の検索画面で誤った比較が出ているかは未確認（この環境から本番に届かない）。

### Cowork が入れた最小の対策（[PATCH]。下の表）
- `src/jan-validity.mjs`（新規）に `isUniqueJan` を移し（#706 と同じ条件）、次で使う：
  - Yahoo! 取込：無効 JAN は商品キーにしない（`YAHOO:店の商品コード` にする）
  - 同一商品判定：無効・共通の JAN／GTIN の一致は根拠にしない
  - 検索結果の重複まとめ：無効 JAN の鍵を作らない
- 回帰テスト：無効 JAN が同じ別商品（別のまま）／正しい JAN の同じ商品（同一のまま）／取込の鍵。
- **していないこと**：既存の価格履歴（`JAN:0000000000000` などの行）の書き換え・削除。承認が要る（下）。今後の記録は新しい鍵（`YAHOO:…`）になるので、古い鍵の行は増えなくなる。
