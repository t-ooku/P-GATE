# HOSHILU マイ最安ルート｜「商品を決めている人」向け購入先決定エンジン

## 0. 要点・競争仮説
ユーザーは「品番・型番・JANまで決めている商品を、大手検索エンジンより早く・確実に・安く買うための独自機能」の実装を希望する。

**市場にない機能と断定しないこと。** 競合には Google Shopping の目標価格追跡、価格.com の最安値通知、Pricey の多EC比較、PLUG の送料等を含む比較、ShopSavvy のバーコード/型番/履歴比較、買い物単価アプリ・家族リストの例が存在する。単純な一括検索・JAN読取・値下がり通知・最安表示だけでは差別化できない。

**本命の差別化仮説**：
> 「自分が買うと決めた**まったく同じ規格**の商品を、**自分の配送条件や買い物リスト**で比較。単品だけでなく**複数品の送料を含めた支払総額**まで比較して、実際の購入ページへそのまま進む。次回は同じ商品と条件を開くだけ。」
「検索」ではなく「個人の買う場所・買い方を選ぶエンジン」。競合に絶対ないとは言わない。複合UXの速度/精度/継続利用で勝つか実証する。

## 2. 独自機能の一貫した体験（MVP→段階拡張）

### M0: 「型番ロック」＆正しい商品だけの比較カード（最初のMVP）
**入力**: 商品名+正式型番/品番、JAN、JANのバーコード、既存の商品URL、既存の検索結果から「いつもの同じ商品を保存」。すでに実装されている入力UI/照合機能を最大限再利用。新規モール検索の無許諾アクセスはしない。

**商品指紋 (exact SKU identity)**:
- manufacturer/brand, maker_model_or_sku, validated_jan_or_gtin, variant_color, shoe_size, capacity/weight, pack_count, refill_or_body, bundle_or_single, condition_import_region, food_flavor_or_temp_class 等の**判明した属性だけ**を構造化。
- 商品を「同一確認済み／矛盾あり／未確定」に分ける。JANが同じでも内容量等が衝突したら未確定・別商品。無効/共通JANと小売店内のコードだけを跨店照合根拠にしない。
- 同一性が未確定な店は価格順位・最安判定から外し、「確認できていない別候補」として示す。ユーザーに選ばせる場合も後続の確定に使った根拠を保持。商品名だけの曖昧一致からロックしてはならない。
- 価格を比較する販売先は商品**詳細ページ**へ直接リンクできる実在オファーのみ。検索ページへのリンクは「モールで再検索」で別表示。

**表示（1画面で判断できる）**:
- 商品を同じと判断した根拠（型番/色/容量/入り数）、比較先数、「確認できた販売先の中での最安」、支払総額の内訳（税込/送料/必須手数料）、配送条件、在庫・確認時刻、購入ボタン。送料無料の例外・会員価格などが未確認なら「不明」と表示し勝者判定から外す。
- 1店舗のみ→「比較未成立」、0店舗→価格比較をしない・既存検索や見張りを案内。全店最安とは言わない。条件付きクーポン・ポイントは客観的に確定できなければ勝手に差し引かない。
- 「いつもの商品としてホシっとく」から次回同じSKUを即確認。まず既存member_wishes / line_watch / local既存UIの安全な利用可能範囲を監査。保存先・権限・D1 migration を勝手に追加しない。
- アフィリエイト・PR順位と価格勝者は独立。広告表記を守る。

**実装範囲**: 新たな全モール収集は行わず、既存の検証済みオファー/直接リンクで実現。検索本体C-1/C-2の受領・本番確認の後、CoworkがCodexへ非競合なM0最小PRを起票する。M0 UIはまずQAフラグ/ステージングで検証、QAを除外し、本番投入する前にCoworkの表示検証とCodexの安全確認を通す。

### M1: 「いつもの買い物」ホーム（再検索不要）
- 日用品や食品の**決まったSKU**を数点保存（洗剤詰替1.2L、シャンプー詰替、化粧品#04等）。「今日の買い先を確認」を押すだけで M0 を一括実行、各品に確認済み購入先へ直リンク。
- 個人情報を最小化。配送の**広域条件**（都道府県/地域例外等）と購入者が明示した会員条件のみを任意保存。正確な住所・カード情報・アカウント資格情報を原則保存しない。ログイン強制は避けるが、永続保存には既存認証・同意を利用。
- 「前回見た価格」「価格が高い・見つからない」「今回の販売先」の区別。購入の発生は推定しない。利用者が「買った」と入力した場合のみ購入済みとして管理。
- 既存の希望価格/LINE値下がり通知に同一SKUを結び付け、重複通知・無効JAN見張りを発生させない。新しい通知媒体/費用は別承認。

### M2: 「まとめ買い最安ルート」（差別化をさらに強める）
**利用者の例**：いつもの洗剤、シャンプー、日焼け止めを買う。各商品の最安値ショップを個別に選ぶと送料が3回発生する場合、同じ店でまとめるほうが総支払額が下がることがある。

- 同一商品と確認した実オファーのみを入力として、**2〜5 SKUから**店別の組み合わせを計算。単品の個別最安合算と、複数SKUのショップ別合算＋確認できた送料・必須費用の「比較可能な案」を出す。
- **店内のカート送料/送料無料閾値が未取得なら、複数SKUを自動でまとめて送料無料と計算しない。** 配送地域・対象店・会員条件・在庫・商品個数・温度帯・分割発送・クーポンの適用条件を反映できない案は「概算・要購入先確認」で勝者順位から除外。数学的には検証済みの送料モデルがある案のみ min(total) を求める。
- 最大の難所は**同一店舗の複数品を一括カート投入できるか**。API/正式連携がなければ「この店の商品ページをそれぞれ開く」まで、決済/自動注文/自動カート投入を偽らない。
- 買い合わせによる差額は「同じ時点・同じSKU・同条件の検証済み代替案」間だけを表示。比較不能なら節約額未取得。計算結果に店舗名・品番・送料ルール・確認時刻を示す。
- まず**外部I/Oの無い純関数/固定価格フィクスチャ**でアルゴリズムを作り、QAの実装とUXを検証。正式な送料・複数商品の扱いを確保できる店舗が現れた時点で現実データをつなぐ。
