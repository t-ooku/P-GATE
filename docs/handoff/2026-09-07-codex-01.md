# 希望価格ウォッチ：商品ID欠落の修正

- 受領：2026-09-07。ユーザーの「では、進めて」に基づく実装・検証・本番反映。
- 起点：`262e8334deff85ff8f3413186e76108e3f764022` / `feature/ui-search-v2`。
- Codexが実装主幹。Claudeによる同時pushは行わない。新機能より希望価格ウォッチの確実性と計測を優先。
- 引継ぎ原文：`2026-09-07-claude-to-codex-primary.md`。原文の9/8(月)は9/8(火)の誤記。

## 原因（コードと回帰テストで確認）

`public/app.js` は既に `record_key` / `asin` を保存していた。
欠落箇所はサーバーの `sanitizePublicCandidate`。楽天・Yahoo!の正規APIから取得した
`record_key` が公開回答の許可リストに無く、ASINを持たない候補は空IDのまま画面へ渡されていた。
したがってクライアントに既存フィールドを再追加するだけでは直らない。

## 修正

1. 公開可能な楽天/Yahoo!商品コード・JAN・ASINだけを `target_product_key` として返す。
   任意の内部record_key、SKU、URLフォールバック、アフィリエイトトークンは公開しない。
2. 希望価格ダイアログはこの公開IDを優先する。会員保存、未ログインのメール/LINE認証待ち、
   購入後ウォッチの各経路で保持。`app.js`の2コピーを同期し、読込版を151に更新。
3. 保存済みIDがある場合はID一致を必須にする。別IDを同じ商品名・型番で一致扱いにしない。
   ハイフンとアンダースコア等を潰さない。IDが無い旧データの判定閾値は変更しない。
4. 同じ商品の空ID再POSTと価格のみPATCHで、保存済みIDを消さない。
5. 既存の読取専用KPI成果物へウォッチ診断を追加。
   ID有無の集計、直近24時間の理由別件数、最終巡回時刻のみ。会員ID・wish ID・商品名は出力しない。
   取得失敗時はUNAVAILABLE。内部テストを含むと明示し、一般利用者の実績とは扱わない。

## 検証と反映

- 回帰テスト：楽天/Yahoo!/JANの正規化→公開回答→会員保存→GET読戻し→巡回照合。
- 実際のダイアログ保存ハンドラ：会員/未ログイン、通常/購入後の各経路。
- 異なる商品IDは安価でも通知ゼロ、NO_MATCHとして記録。
- ローカル `npm test` 成功（Worker 2,259件、release 6件、拡張6件およびGASテスト）。検索品質チェック成功。デプロイ状態は反映後の実測で報告する。
- DBスキーマ変更・既存会員データの一括修正・SNS投稿・価格変更はこの変更に含まない。

## 制約と残作業

- モール固有商品コードを持つウォッチは、その商品コードで確認できた候補を対象とする。
  同じJANを共有する候補は一致する。異なる出品コードを商品名だけで同一扱いにはしない。
- 旧データの空IDは後から商品名で推測して埋めない。原データ/元の商品が確認できる場合だけ修復する。
- 巡回は引き続き検索APIを使うため、対象商品が検索結果に含まれない場合は見つからない。
  商品IDによる直接取得は次の検討事項。
- 価格データ保存は未実装。各モールの現行条件・保存先スキーマ・取得時刻と有効期限を確認してから設計する。
- 一般ユーザーの自発的Watch Set、通知後再訪、モール送客は実数を確認するまで達成扱いしない。
