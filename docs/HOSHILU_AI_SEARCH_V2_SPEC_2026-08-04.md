# HOSHILU AI Search v2.0 仕様書

更新日: 2026-08-04
対象ブランチ: `agent/mygate-v5-itg-phase0`
正式名称: HOSHILU（ホシル）

## 1. 目的

HOSHILU AI Search v2.0 は、ユーザーの長い・曖昧な自由文をAIが理解し、商品候補・特徴・複数の検索キーワードへ構造化したうえで、HOSHILU自身が複数モールとSNSを横断検索する仕組みである。

AIを商品検索エンジンとして扱わず、意図理解エンジンとして扱う。

原則:

- AIは考える。
- HOSHILUは探す。
- AIに商品URLを生成させない。
- 購入先・価格・在庫・商品URLはHOSHILU側で取得・検証する。

## 2. 解決する課題

ユーザーは商品名を知らないことが多く、次のような曖昧文で検索する。

- 韓国っぽくて透明で、ケースも中身も見えるワイヤレスイヤホン
- TikTokで見た、光る小さいスマホケース
- 名前は分からないが、机の上で使う白い家電
- 日本で使える米国限定の商品

従来方式ではAIに直接商品URL・引用・商品ページ情報まで要求していたため、タイムアウト、引用0件、検証0件が発生しやすかった。

v2.0では、AIが得意な「意味理解・候補生成・検索語変換」に限定する。

## 3. 基本アーキテクチャ

```text
ユーザーの曖昧文
  ↓
AI意図理解（Gemini優先）
  ↓
構造化データ
  ├─ カテゴリ
  ├─ 特徴
  ├─ 商品候補 3〜5件
  ├─ 一致率
  ├─ 推薦理由
  ├─ 日本語検索語
  ├─ 英語検索語
  ├─ 中国語検索語
  └─ 韓国語検索語
  ↓
HOSHILU検索エンジン
  ├─ Amazon
  ├─ 楽天市場
  ├─ Yahoo!ショッピング
  ├─ Qoo10
  ├─ SHEIN
  ├─ ZOZOTOWN
  ├─ SHOPLIST
  ├─ MUSINSA
  ├─ BUYMA
  └─ SNKRDUNK
  ↓
SNS検索
  ├─ Instagram
  ├─ X
  ├─ TikTok
  └─ YouTube
  ↓
商品候補・価格・画像・購入先・推薦理由を表示
```

## 4. AIの役割

AIは次だけを担当する。

1. 曖昧文の意図理解
2. 商品カテゴリ推定
3. 重要特徴の抽出
4. 商品候補名の生成
5. 長い文章を複数の短い検索語へ変換
6. 表記ゆれ・同義語・英訳・中国語・韓国語の生成
7. 各候補の一致率と推薦理由の生成

AIは次を行わない。

- 商品URLの生成
- 価格の生成
- 在庫の断定
- 未確認の型番の創作
- 商品ページの直接検証
- アフィリエイトURLの生成

## 6. 多言語仕様

対応言語:

- 日本語
- 英語
- 中国語
- 韓国語

必須ルール:

- 入力原文を保持する。
- ブランド名・型番は原文を優先する。
- 表示文言は選択中の言語へ合わせる。
- 推薦理由も選択中の言語で返す。
- 日本のモールは日本語＋英語を優先する。
- Qoo10、SHEIN、MUSINSA、SNSは原文＋英語＋対象言語を使い分ける。
- 原文の意味を変えない。
- 翻訳語だけに置き換えず、原文と翻訳語を併存させる。

## 7. モール検索語の選択ルール

### Amazon

優先順位:

1. 候補の商品名
2. ブランド＋モデル
3. 日本語短縮語
4. 英語短縮語

### 楽天市場

優先順位:

1. 日本語の商品名
2. 日本語カテゴリ＋特徴
3. 日本語の短縮語

### Yahoo!ショッピング

優先順位:

1. 商品名
2. 日本語短縮語
3. 英語ブランド名

### Qoo10

優先順位:

1. 日本語短縮語
2. 英語短縮語
3. 韓国語短縮語

### SHEIN / MUSINSA

優先順位:

1. 英語短縮語
2. 韓国語短縮語
3. 原文

### SNS

- 原文を必ず保持する。
- 商品名候補、特徴語、ハッシュタグ候補を併用する。

## 8. 画面表示仕様

候補ごとに次を表示する。

- 商品候補名
- ブランド
- 一致率
- 推薦理由
- 一致した特徴
- モール検索ボタン
- 商品画像（取得できた場合）
- 価格比較（取得できた場合）
- 在庫・送料・配送目安（確認できた場合のみ）

表示例:

```text
Nothing Ear   95%
透明デザインと完全ワイヤレスという条件に最も近い

一致した特徴:
透明 / スケルトン / 完全ワイヤレス

Amazon | 楽天市場 | Yahoo! | Qoo10 | SHEIN
```

確認できていない情報は断定しない。

## 9. AIプロバイダー

優先順位:

1. Gemini API
2. OpenAI API

Gemini失敗時のみOpenAIへフォールバックする。

失敗条件:

- タイムアウト
- 429
- JSON不正
- 候補0件かつ検索語0件
- プロバイダー障害

OpenAI API残高がない場合は、通常のHOSHILUモール検索へフォールバックする。

## 10. キャッシュ・AI辞書

目的は、同じ検索のたびにAIを呼ばないことである。

### 完全一致キャッシュ

正規化後の条件が完全一致した場合、AI結果を再利用する。

### 構造化条件キャッシュ

次の主要条件が一致した場合だけ部分再利用する。

- カテゴリ
- 必須特徴
- 除外条件
- 価格条件
- 用途
- 色
- ブランド条件

文章の類似度だけでは再利用しない。

### 部分再利用

再利用できるもの:

- 商品候補名
- 検索キーワード
- 同義語
- 多言語語句

毎回再取得するもの:

- 価格
- 在庫
- 配送
- 商品URL
- 販売状況

### D1保存候補

- normalized_intent_hash
- category
- features_json
- exclusions_json
- price_conditions_json
- product_candidates_json
- multilingual_keywords_json
- provider
- model
- created_at
- updated_at
- expires_at
- reuse_count
- click_feedback_json

## 11. ユーザー行動による改善

将来、次の行動を集計してランキングに利用する。

- 候補クリック
- モールクリック
- ほしっとく保存
- 購入先遷移
- 検索し直し
- 候補非選択

AI出力を無条件に学習結果として採用しない。

ユーザー行動は、候補順位の補助信号として使う。

## 12. コスト制御

個人経費での運用を前提とする。

必須:

- AI呼び出し回数を記録
- プロバイダー別トークン数を記録
- 1検索あたり推定費用を記録
- 1日・1か月の予算上限を設定可能にする
- 上限到達時は通常モール検索へ切り替える
- 同一検索の連打を抑止する
- キャッシュ命中率を可視化する

自由文検索では高いキャッシュ命中率を前提にしない。

初期試算は、実測トークン数・検索回数・キャッシュ非命中率を用いて行う。

## 13. セキュリティ・品質

- APIキーをクライアントへ露出しない。
- ユーザーの自由文を不要にログへ保存しない。
- 個人情報を検索語から除去する。
- AI出力を信頼せず正規化・検証する。
- 商品URLは許可ドメイン・正規化・追跡URL生成を経由する。
- 価格・在庫・配送は取得できた値だけ表示する。
- AIの内部思考過程は表示しない。
- ユーザーには短い推薦理由と一致特徴だけを表示する。

## 14. 実装フェーズ

### STEP1: AI意図理解

状態: 実装済み・テスト済み

- URL要求を廃止
- 商品候補生成
- 特徴抽出
- 複数検索語生成
- 4言語検索語生成
- Gemini優先、OpenAIフォールバック

### STEP2: 候補別モール検索接続

状態: 実装済み・テスト済み（2026-08-05）

- 候補ごとの検索語選択（AIが生成したsearch_keywordsを使用、無ければ候補名にフォールバック）
- 候補ごとのモール検索リンク（index.mjsのaiDiscoveryWithSignedCandidateLinks()が、
  全文検索フォールバックと同じsignedMarketplaceSearchLinks()経由で候補ごとに署名付き
  /goトラッキングリンクを生成。AIが生のURLを作ることはない）
- 4言語表示（既存の多言語プロンプト・aiIntentLabelsで対応）
- 推薦理由・一致率表示（従来は先頭候補のみ表示だったのを、public/app.jsの
  aiCandidateCards()で返却された全候補に拡張）

### STEP3: 実商品検索・価格比較

- API接続済みモールで商品候補を取得
- 画像・価格・送料・在庫・配送を統合
- 候補単位で価格比較

### STEP4: D1キャッシュ

- 完全一致キャッシュ
- 構造化条件キャッシュ
- TTL
- 再利用回数
- 費用記録

### STEP5: 行動学習

- クリック・保存・再検索の集計
- 候補順位への反映
- 管理画面での可視化

## 15. 完了条件

次を満たした時にAI Search v2.0完成とする。

- 4言語すべてで曖昧文を解析できる。
- 商品候補3〜5件を返せる。
- 複数の短い検索語を返せる。
- 候補ごとに主要モール検索へ進める。
- 推薦理由と一致率が表示される。
- AI失敗時も通常検索が使える。
- APIキーや機密情報が露出しない。
- 全自動テストが合格する。
- 本番Workerへデプロイできる。
- 1検索あたりのAI費用を測定できる。

## 16. 開発ルール

- 本仕様書をHOSHILU AI Search v2.0の基準とする。
- 独自に「AIへURLを返させる方式」へ戻さない。
- 既存の10モール・SNS検索を壊さない。
- 既存の4言語UIを壊さない。
- 既存テストに加えて新仕様の回帰テストを追加する。
- テスト失敗中は本番デプロイしない。
- GitHub保存後、ローカル取得、テスト、本番デプロイ、実機確認の順で進める。

## 17. 設計原則

> AIは「何を欲しがっているか」を理解する。
>
> HOSHILUは「どこで買えるか」を探す。

この役割分担をHOSHILUの中核アーキテクチャとする。
