# HOSHILU AIウォッチ 将来設計 v0.1（2026-08-05, CTO指示v3.2 ⑤）

## 0. 位置づけ

本書は**設計のみ**であり、コード実装は含まない。CTO指示書v3.2 ⑤「AIウォッチ将来設計」の要求に基づき、現行実装済みの4項目(値下げ／クーポン／再入荷／販売開始)に加え、将来追加予定の6項目の設計方針を記録する。

## 1. 現行実装済み(v3.2で対応)

`teacher_queries`等とは独立した監視対象。UIは「AIウォッチ」ダイアログ(商品カードのベルアイコンから開く)で以下4条件を選択可能:

- 値下げ
- クーポン
- 再入荷
- 販売開始

保存先: `localStorage`の`hoshilu_watch_preferences`(クライアント側)。将来、無料会員ログイン時はサーバー側(`member_wishes`等の既存テーブル)へも同期される設計を維持する。

## 2. 将来追加予定の6項目

| 項目 | 判定に必要なデータ | 実装難易度(概算) | 備考 |
|---|---|---|---|
| 他モール最安値 | 同一商品の複数モール価格(`offers[]`)を横断比較 | 低〜中。既存の`offers`配列とマーケットプレイス統合基盤(`rankMerchantCandidates`等)を再利用可能 | 「Amazonで見ていた商品が楽天の方が安い」を検知 |
| 類似商品の方がおすすめ | 同一`product_type`内の他候補との比較(価格・レビュー・スペック) | 中〜高。類似度判定ロジックが未実装(Teacher Dataset/構造化クエリ基盤の拡張が前提) | 誤検知(無関係商品の誤推薦)を防ぐガードが必須 |
| 新型発売 | 型番・世代情報の追跡(例: iPhone 15→16) | 中。`apparel-query-attributes.mjs`等が持つ世代・型番検出ロジックを応用可能 | メーカー公式情報源との突合が必要 |
| 偽物注意 | 出品者の信頼性シグナル、価格が異常に安い等のヒューリスティック | 高。誤判定が販売者への風評被害になり得るため慎重な設計が必要 | 断定ではなく「注意喚起」の表現に留める方針(既存のURL未確認商品の扱いと同じ思想) |
| 値上げ予測 | 価格履歴の時系列データ蓄積が前提 | 高。価格履歴を蓄積するデータ基盤(新規テーブル)が未着手 | 予測モデルではなく、まずは価格履歴の可視化から段階導入する方が安全 |
| 買い時診断 | 上記複数シグナル(価格推移・セール周期・在庫状況)の統合判断 | 高。他の5項目が前提条件となる複合機能 | 最後に実装する項目と位置づける |

## 3. Teacher Datasetとの接続(⑥参照)

[HOSHILU_TEACHER_DATASET_SPEC_v1.0.md](HOSHILU_TEACHER_DATASET_SPEC_v1.0.md)で設計した`teacher_queries`は検索品質の教師データだが、将来的にAIウォッチの誤検知率(偽物注意・類似商品推薦の精度)を検証するための教師データとしても再利用する設計とする。`migrations/0034_teacher_dataset_watch_columns.sql`で追加した`price_watch`／`stock_watch`／`coupon_watch`／`launch_watch`列(現時点では列のみ、ロジック未接続)は、将来「この検索文に対して、どの監視項目が有効であるべきか」をGPTが教師データとして起票できるようにするための布石。

## 4. 段階的導入案

| Stage | 内容 | 判定基準 |
|---|---|---|
| 0(v3.2で完了) | 値下げ／クーポン／再入荷／販売開始の4項目、UI実装済み | 完了 |
| 1 | 他モール最安値。既存`offers[]`比較ロジックの追加のみ、新規データ基盤不要 | 実装コストが最も低いため次点候補 |
| 2 | 新型発売。型番検出ロジックの拡張 | 既存の型番検出パターンを再利用可能な範囲で先行 |
| 3 | 価格履歴データ基盤の新設(D1新テーブル、日次スナップショット) | 値上げ予測・買い時診断の前提条件 |
| 4 | 値上げ予測・買い時診断 | Stage3のデータが一定期間(最低数週間)蓄積されてから着手 |
| 5 | 類似商品の方がおすすめ・偽物注意 | 誤検知時の影響が大きいため、Teacher Datasetによる精度検証(§3)を経てから本番投入 |
